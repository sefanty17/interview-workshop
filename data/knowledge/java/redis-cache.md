# Redis 缓存设计与一致性

## 缓存穿透、击穿、雪崩

穿透：查询一个数据库里也不存在的 key，缓存永远不会命中，请求全打到数据库。典型来源是恶意攻击或脏参数。解法有三种：一是缓存空值（给 null 也设一个短 TTL，比如 60 秒）；二是布隆过滤器，把所有可能存在的 key 预先放进去，不存在直接拦掉；三是入口参数校验，把明显非法的 key 挡在业务之前。

击穿：某个热点 key 过期的一瞬间，大量请求同时打到数据库。解法是加互斥锁（只有拿到锁的线程去回源，其余等待或返回旧值），或者热点 key 逻辑过期（不设 TTL，值里带过期时间戳，过期后异步刷新）。

雪崩：大量 key 在同一时刻集中过期，或者 Redis 实例挂掉。解法是 TTL 加随机抖动、做多级缓存、Redis 集群高可用、以及限流降级。

三者的区别记法：穿透是「查不到」，击穿是「一个热点没了」，雪崩是「一片同时没了」。

## 缓存与数据库的一致性

先更新数据库再删缓存（Cache Aside），是工程上最常用的方案。为什么不先删缓存再更新数据库？因为删完到更新完成之间有空窗，别的请求会把旧值读回缓存。

为什么是删而不是更新？因为并发更新缓存的顺序不可控，可能出现旧值覆盖新值；删除是幂等的，代价也更低。

删除失败怎么办：用消息队列或 binlog 订阅（Canal）做重试删除，保证最终一致。延迟双删（更新后删一次，延迟几百毫秒再删一次）能缓解一部分问题，但延迟时间靠经验，并不可靠。

强一致要付出代价：分布式锁 + 读写都加锁，性能会掉一个量级。绝大多数业务能接受短暂不一致，所以别再追求「缓存和数据库时刻一致」。

## 数据结构与适用场景

String：缓存对象、计数器（incr）、分布式锁（setnx + expire，注意要用原子命令 set key value NX EX 10，不要分开两条）。

Hash：存对象的多个字段，可以单独更新某个字段。小 Hash 在元素少时用 ziplist/listpack 编码，内存占用很低。

List：简单的消息队列（lpush + brpop）、最新列表。

Set：去重、交并差（共同关注、标签筛选）。

ZSet：排行榜（按分数排序）、延时队列（用时间戳做 score，定时任务 zrangebyscore 取到期任务）。

Bitmap：签到、活跃用户统计，一个用户一天一个 bit。HyperLogLog：基数统计（UV），占用固定 12KB，误差 0.81%。

## 持久化与过期策略

RDB：定时生成全量快照。恢复快，但会丢最后一次快照之后的数据，fork 时可能阻塞（大实例上 fork 有毫秒级到秒级停顿）。

AOF：追加写命令日志。appendfsync 三档：always（每次刷盘，最安全最慢）、everysec（每秒刷，默认，最多丢一秒）、no（交给操作系统）。AOF 文件会膨胀，需要重写（bgrewriteaof）。

Redis 4.0 之后支持混合持久化：重写时前半部分是 RDB 格式，后半部分是增量 AOF，兼顾恢复速度与数据完整性。

过期删除策略是惰性删除 + 定期删除：访问时才判断是否过期，同时每 100ms 随机抽查一批 key 删掉过期的。所以内存里可能残留已过期但没被删的 key。

内存淘汰策略八种，常用的是 allkeys-lru 与 volatile-lru（只淘汰设置了过期时间的）。如果拿 Redis 当纯缓存，用 allkeys-lru；如果里面混了不能丢的数据，用 volatile-lru，并把持久数据设成不过期。

## 分布式锁的正确姿势

加锁：set key value NX EX 10，value 必须唯一（UUID），代表持有者。

解锁必须用 Lua 脚本，先比对 value 再删除，否则可能删掉别人的锁：
if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end

锁超时了但业务没跑完怎么办：用看门狗续期（Redisson 的 watchdog 默认每 10 秒续一次，续到 30 秒）。自己实现需要额外的续期线程，容易出错。

主从架构下的锁失效问题：主库加锁成功但还没同步到从库就宕机，从库升主后锁丢失。Redlock 试图用多数派解决，但争议很大（Martin Kleppmann 与 antirez 的著名辩论）。工程上更稳妥的做法是用 ZooKeeper/etcd 的临时顺序节点，或者在业务层做幂等，不完全依赖锁。
