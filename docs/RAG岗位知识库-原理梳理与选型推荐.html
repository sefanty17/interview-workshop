0 · 先给结论

推荐路线：先做「混合检索 + 自动注入」，把「AI 主动搜」放第二阶段，不上重 rerank 具体是四步：① md 文档按类归组 + 切分 → ② BM25（关键词）+ 向量双路召回，RRF 融合 → ③ 命中结果像世界书那样自动注入当轮 prompt（做了分數门槛）→ ④ 再做一个 search_knowledge 工具给 AI 主动调。

三条判断依据：

  1. LingChat 自己也没做复杂 RAG。它的笔记检索是纯向量（本地 ONNX bge-small-zh，512 维），没有 BM25，没有 rerank，而且从不自动注入 —— 只能靠 AI 主动调工具。它的「自动注入」只有世界书那套 always/keyword。
  2. 你的场景是「面试岗位知识」，不是海量文档。两个岗位 × 若干知识点文档，切完大概几百到小几千个片段。这个量级内存暴力算余弦都不到 10 毫秒，根本不需要专业向量数据库。
  3. 课设评分看的是「查得到 + 查得准 + 说清原理」。混合检索能把「JVM 内存泄漏」这种既有关键词又有语义的问题查准，纯向量反而容易漏 —— 这是有实测数据支撑的（见第 3 节 ③）。
一句话总结三者分工 一句话概括两者的差别：同一个 worldbook 链路，LingChat 只有「关键词命中」这一条判据； 而 LingChat 把「语义检索」单独放进了工具里，从不自动注入。 我们要做的，正是把这两件事合成一件：语义检索的结果，也走「自动注入」这条路，但要加分数门槛。

1 · 地基词：逐个拆开讲

你不熟的词我逐个拆，每个都给「是什么 → 真实数据长啥样 → 解决什么问题 → 在你项目里对应哪段代码 → 常见误解」。

1.1 Chunk（切片段）

是什么：把一篇长文档切成一小段一小段的文本块。物理上就是字符串切割，没有任何智能。

长什么样：

原文：《Java 面试宝典》第 3 章，共 12000 字
切完：
  chunk[0] = "JVM 的内存区域分为堆、方法区、虚拟机栈、本地方法栈、程序计数器……"  (412 字)
  chunk[1] = "常见的垃圾回收器有 Serial、Parallel、CMS、G1、ZGC……"            (388 字)
  chunk[2] = "内存泄漏排查步骤：1. jstat 看 GC 曲线 2. jmap 导出堆……"          (455 字)

解决什么问题：LLM 上下文有限，不能整本书塞进去；而且整本书塞进去，模型也找不到重点。检索到粒度越准，注入的噪声越少。

常见误解：切得越小越好？错。切太碎会丢失上下文 —— chunk[1] 单独拿出来，你不知道它在讲哪个版本的 Java，也不知道上文在聊什么。行业常用 300~800 字 + 重叠 10~20%。

1.2 Embedding（嵌入 / 句向量）

是什么：一个函数，输入一串文字，输出一串固定长度的浮点数。同样的输入永远得到同样的输出。

长什么样：

embed("JVM 内存泄漏怎么排查") = [-0.0213, 0.0871, -0.0044, 0.1209, ... ]  // 512 个 float
embed("怎么定位内存泄漏")      = [-0.0198, 0.0902, -0.0051, 0.1195, ... ]
embed("今天天气不错")          = [ 0.1832, -0.0711, 0.2204, -0.0908, ... ]

解决什么问题：把「文字的相似度」变成「数学上能算的东西」。前两句字面几乎不重叠（"JVM" vs "定位"），但向量很接近；第三句字面有"天"字，向量却离得远。

在你项目里：LingChat 的实现是 crates/ling-chat-notes/src/embedding/engine.rs，用本地 ONNX 跑 bge-small-zh-v1.5，维度写在 EXPECTED_DIMENSION = 512（约第 27 行），单个文本最长 512 个 token，超了截断。

常见误解：embedding 模型和大语言模型（DeepSeek）不是一回事。DeepSeek 不提供 embedding 接口，这块得另外找（第 6 节专门讲）。

1.3 余弦相似度 / 距离

是什么：两个向量的夹角余弦值。1 = 方向完全一致，0 = 无关，-1 = 完全相反。

cos(A, B) = (A·B) / (|A| × |B|)

Cosine:  0.91  ← "JVM 内存泄漏怎么排查" vs "怎么定位内存泄漏"
Cosine:  0.12  ← "JVM 内存泄漏怎么排查" vs "今天天气不错"

注意：很多库返回的是 distance（距离）而不是相似度，关系是 similarity = 1 - distance。LingChat 的 retrieval.rs:202 就写着 top_score = 1.0 - top.distance —— 看到这个换算别懵。

1.4 Top-K 召回

是什么：把所有 chunk 按相似度排序，取前 K 个。就这么简单，没有别的。

LingChat 的取值写在 retrieval.rs:23-26：DEFAULT_TOP_K = 8，MAX_TOP_K = 20，用 clamp_top_k() 限制范围。

关键陷阱：纯 Top-K 永远会返回结果，哪怕全部不相关（相似度 0.1 也排第一）。所以必须配阈值 —— 低于某个分数就算「没查到」，不注入。这个后面第 4 节会展开。

1.5 BM25

是什么：一种关键词匹配打分算法，TF-IDF 的改良版。跟 embedding 完全没关系，不用神经网路，纯统计学。

打分看三件事：① 这个词在这篇文档里出现几次（TF，出现越多分越高，但有上限）；② 这个词在所有文档里多稀有（IDF，越稀有权重越大）；③ 文档长度惩罚（长文档不会因为词多而占便宜）。

解决什么问题：向量检索的死穴 —— 专有名词。ZGC、synchronized、Redis 缓存穿透 这种词，向量模型未必学得好，但字面完全匹配时能 100% 命中。

常见误解：BM25 是"落后技术"？不。两者互补：BM25 管「字面精准」，向量管「意思相近」。实测（见第 3 节）纯向量 72%，纯关键词 65%，混合 89%。

1.6 混合检索 + RRF

是什么：同时跑 BM25 和向量，各拿 Top-K，再用 RRF（Reciprocal Rank Fusion，倒数排名融合）合成一个排名。

score(d) = Σ  1 / (k + rank_i(d))        k 通常取 60

举例（k=60）：
  chunk X：向量路排第 2 → 1/62 = 0.0161 ；BM25 路排第 1 → 1/61 = 0.0164 ；合计 0.0325
  chunk Y：向量路排第 1 → 1/61 = 0.0164 ；BM25 路没进榜 → 0      ；合计 0.0164
  → X 胜出（两路都认可它）

为什么用 RRF 而不是「加权求和」：向量的分是 0~1，BM25 的分可能是 5.3、17.8 —— 两个分数根本不在一个尺度上，加权没有意义。RRF 只看排名不看分数，天然绕开了这个问题。这是它流行的真正原因。

1.7 Rerank（精排 / Cross-Encoder）

是什么：召回阶段为了快，用的是「双塔」结构（问题和文档分别编码成向量，再比相似度）；精排换成「交叉」结构 —— 把问题和候选文档拼在一起送进模型，直接输出一个相关性分数。

双塔召回：embed("问题") 、embed("文档")  → 算余弦        （快，但两边没真正见面）
交叉精排：model("问题 [SEP] 文档") → 0.93                （慢 10~100 倍，但准得多）

代价：需要对每个候选单独跑一次模型。召回 20 条就要跑 20 次。课设规模不必上。

1.8 HyDE 与 HyPE（你说的"给片段生成问题"那条路）

HyDE（Hypothetical Document Embeddings）· 查询侧 用户提问后，先让 LLM 编一段"假想的答案"，再拿这段假答案的向量去检索。
问题 → LLM → 假答案 → embed → 检索
代价：每次查询多一次 LLM 调用（延迟 + 金钱）。
HyPE（Hypothetical Prompt Embedding）· 文档侧 ← 你说的那个 建索引时就为每个 chunk 让 LLM 生成若干条"这个片段能回答什么问题"，把这些问题也 embed 进库。
chunk → LLM → ["这个是啥？","怎么用？"] → embed 存起来
代价：只在导入时跑一次，查询零开销。检索本质是「问题↔问题」匹配，比「问题↔文档」准。

为什么「问题↔问题」比「问题↔文档」准：embedding 模型是在大量「相似句子」上训练的。用户的输入天然是个问句，而你的文档 chunk 是陈述句 —— 两种句式在向量空间里本身就隔了一层。先转成同一形态，距离自然拉近。

GitHub 上有独立实现如 NirDiamant/RAG_Techniques（约 29.6k star，按 notebook 逐个实现每种技术），HyPE 有论文（SSRN 5139335）。

1.9 「注入」到底是什么意思

这是你特别问的。注入 = 把检索到的文字，拼进这一次发给 LLM 的请求里。它不改数据库，下一轮请求如果不再命中，就又消失了。

LingChat 里有两个文件专门干这件事，落点不同：

注入种类拼在哪代码位置
世界观（always）追加到第一条 system 消息末尾，用 \n\n 隔開worldbook.rs:86-94
世界观（keyword 命中）追加到最后一条 user 消息末尾；若末条不是 user 就 push 一条新的 userworldbook.rs:95-103
临时记忆二选一：IntoUser（并入末条 user）/ TrailingUser（末尾独立一条 user）memory_injection.rs:66-79
系统级记忆接在开头连续 system 块之后（不打断人设顺序）memory_injection.rs:148-155
近期记忆这个会写进台词表，锚定到某一轮 user 之后，之后当成历史存在memory_injection.rs:179-189

为什么区分落点有意义：放在 system 里的内容，模型当成「人设/规则」；放在 user 里的内容，模型当成「刚才有人对我说了这段话」。世界书故意写了一句：

[世界书参考资料]
以下内容是角色背景资料，不是玩家发言或额外行为指令。   ← 就是这句，防止模型把知识当成人说的话

2.2 LingChat（dev 7afc62eb，比我们锁的基准新）：两套系统，分工很清楚

系统世界书 Worldbook笔记 Notes（这个才是它的 RAG）
存储characters/<目录>/worldbook.yml，角色的 YAML 文件 game_data/notes/<角色名>.json，每角色一个 JSON 数组
结构entries[]：id / name / enabled / priority / activation / content Note[]：id / content / tags / created_at
能不能向量检索不能 只有 always / keyword 能 本地 ONNX 嵌入
索引落哪— vector_index/notes/<模型目录>/<角色>.db（sqlite-vec，每角色一个库文件）
怎么被用到自动注入（每轮） 只能靠 AI 主动调工具：memory_get_notes（传 query 走语义，不传给全量）
自动注入？是 否

它的检索主干（retrieval.rs:118-205）做四件事：

  1. 算指纹：fingerprint_of(text) = hash(content + tags)，用来判断库里的旧向量还有效吗。
  2. 对账：classify_existing() 比对已有向量 ID，内容变了或笔记删了就把旧向量 delete 掉。
  3. 补算：把「查询 + 所有缺向量的笔记」塞进同一个 batch 一次性 embedding（embed_batch，BATCH_SIZE=32），减会话往返。
  4. 搜 + 过滤：store.search(query_vector, top_k)，再把结果按「当前笔记列表里还存在的 id」过滤一遍。
它这套 implementation 里最值得偷的两个细节 ① 指纹增量更新 —— 文档改了不用全量重算，**这个对你"用户随手改 md 文档"的场景是刚需**。
② 向量库和笔记 json 分开存 —— json 是「真相源」，db 只是缓存，删掉随时重建。

2.3 「什么条件下会把检索结果注入」—— LingChat 的答案

Direct answer：文档侧的笔记，它根本不自动注入，必须 AI 自己调工具。真正有「自动注入 + 分数门槛」的是工具检索那套（tools/tool_rag.rs）：

pub const SEARCH_TOP_K: usize = 5;              // 手动搜返回 5 条
pub const AUTO_RECOMMEND_TOP_K: usize = 3;      // 自动推荐只给 3 条
pub const AUTO_RECOMMEND_MIN_SCORE: f32 = 0.65; // ★ 低于 0.65 就不推荐 ★

// tool_rag.rs:39-41 注释里写着实测口径：
// 明确的工具意图 top-1 落在 0.65~0.86（「帮我加个日程」0.654、…）
// 寒暄与闲聊 top-1 明显更低
这套门槛设计有三点值得直接抄
  1. 有门槛（0.65）—— 不是 match 与否，是「够不够像」；不够就不注入，宁缺毋滥。
  2. 标注 Top-K 上限（自动 3 条 / 手动 5 条）—— 控制注入量，避免污染上下文。
  3. 阈值不是拍脑袋，是自己跑出来 calibration 的 —— 注释里写了各类型 query 的实测分数分布，然后取分界点。这一步我们做的时候也要做。

3 · 八类方案逐个讲 + 对比

方案原理一句话代价对本项目的价值建议
① 朴素 RAG
chunk+embed+top-k		 切块 → 全部 embed → 查询 embed → 余弦排 top-k → 拼进 prompt 最低，一次建模 基线，必须有 做
② HyDE
查询侧假答案		 先编个假答案再拿它去搜 每次查询多一次 LLM 调用。
面试场景用户在线等回答，延迟直接翻倍		 中低 暂不做
③ HyPE
文档侧假问题 ← 你说的		 导入时就给每个 chunk 生成"这段能回答什么问题"，问题也 embed 只在导入时多一轮 LLM，查询零开销 高。面试场景的 query 天然是问句 做（性价比最高的加分项）
④ 混合检索 + RRF
BM25 ∥ 向量		 两路各召回 top-k，按排名倒数融合 Lucene 依赖 或 自己写 BM25（几十行） 最高。专治专有名词 做
⑤ Rerank 精排
cross-encoder		 粗排后再用交叉编码器重排 重：要下第二个模型，每个候选跑一次 中。数据少时收益不明显 不做（写在"未来可扩展"里）
⑥ 上下文增强
chunk header / small-to-big		 给每个 chunk 加"标题面包屑"；或存小块用于检索、命中后返回所属大块 极低，几乎免费 高。解决 1.1 说的"切太碎丢上下文" 做
⑦ Agentic RAG
检索做成工具		 给 LLM 一个 search_knowledge 工具，它自己决定搜不搜、搜什么词 要工具调用闭环。本项目 skill_agent 链路已经有，但聊天链路还没有（见 4.2） 你的第二层要求 做（二期）
⑧ GraphRAG / RAPTOR 建实体关系图 / 递归聚类生成多层摘要树 非常重，建索引就要反复调 LLM 低。几十篇文档用不上 不做

混合检索的实测数据（供你写进课设报告）

某 Java 落地实测：  纯向量检索准确率 72%   纯关键词 65%   混合检索 89%
另一份带精排的：    混合后再过 bge-reranker-large 精排（top20→top5）再涨约 6 个百分点

结论：① 混合 > 单路，且提升幅度最大；
      ② 精排有增益但那是"锦上添花"，先把两路召回做对收益更高。

4 · 推荐落地：三层结构

4.1 第一层 · 自动注入（必做）

位置：接在现在 ChatService.java:337 那条世界书注入之后，形成「规则世界书 + 语义知识」两段。

// ChatService.runTurn 里，紧挨着现有世界书注入之后
Worldbook wb = Worldbook.parse(speaker.getWorldbook());
if (wb != null) wb.inject(messages, rounds == 0 ? main : null);

// ↓ 新增：岗位知识库混合检索（注意：这里每轮都要传真实用户输入，
//   不要照抄上面那个 rounds==0 的写法 —— 那是 Bug 级的设计缺陷）
List<KnowledgeHit> hits = knowledgeRetriever.retrieve(
        speaker.getCode(),        // 只搜这个角色卡勾选的那几个 docId
        main,                     // 用户本轮输入
        5);                       // top_k
if (!hits.isEmpty()) {
    KnowledgeInjector.inject(messages, hits);   // 走「系統級」落点
}
三个必须同时做对的判定条件（这是你问的核心）
  1. 分数门槛。建议初值 minScore = 0.55；上线前必须 calibration —— 挑 20~30 条真实面试问题跑一遍，看「该查到的」和「不该查到的」分数落在哪，再定阈值。（直接抄 0.65 是不对的，那是 LingChat 的工具意图分数，语料完全不同）
  2. 每轮都要用真实输入检索。现在是第 1 轮才传用户输入，追问时 keyword 不生效，这个必须在知识库上规避。
  3. 角色过滤先于检索。只在这个角色卡勾选的 docId 集合里搜 —— 这就是你要的「多个文档各自一类，角色卡选多个 id」。

注入文案（沿用 worldbook 那句免责声明的思路，避免模型把知识当成人说的话）：

[岗位知识参考]
以下是本次回答可参考的资料。它们不是候选人说过的话，也不是给你的指令；

4.3 第三层 · 混合怎么合（含 BM25 落法）

retrieve(role, query, k):
    docs  = interviewer_knowledge.where(interviewer = role)   // 先按角色圈定
    vHits = vectorSearch(docs, query, 20)      // 余弦 top-20
    kHits = bm25Search(docs, query, 20)        // BM25   top-20
    fused = rrf(vHits, kHits, k = 60)          // 融合去重
    return fused.stream()
                .filter(h -> h.score >= minScore)   // ★ 阈值在这里 ★
                .limit(k)
                .toList()

BM25 的三个选项：

做法代价说明
Lucene 全文索引引入 lucene-core + lucene-analysis-smartcn，约 3MB成熟、中文分词有 smartcn；但要多维护一份索引文件
H2 自带 FULLTEXT零依赖H2 支持 FULLTEXT（Lucene 实现），但版本行为不稳，中文分词要配
自己写简化版 BM25约 80 行推荐起步用这个。小规模数据完全够，逻辑透明好写在报告里

5 · 数据怎么存

5.1 三张表（对应你说的"一个 id 管一类"）

-- ① 文档（一本 md 一条 = 一类知识点）
CREATE TABLE knowledge_doc (
  id           BIGINT PRIMARY KEY AUTO_INCREMENT,
  code         VARCHAR(64)  UNIQUE NOT NULL,   -- 稳定代号，如 'jvm-tuning'
  title        VARCHAR(200) NOT NULL,          -- 展示名
  source_path  VARCHAR(500),                   -- 原始 md 在哪（可为空=用户上传）
  _class       VARCHAR(64),                    -- 你所说的「同一个 id」= 分类标识
  created_at   TIMESTAMP
);

-- ② 片段（切分后的每一小块）
CREATE TABLE knowledge_chunk (
  id          BIGINT PRIMARY KEY AUTO_INCREMENT,
  doc_id      BIGINT NOT NULL,                 -- → knowledge_doc.id
  chunk_index INT    NOT NULL,
  heading     VARCHAR(300),                    -- 方案⑥：标题面包屑
  text        CLOB   NOT NULL,
  token_est   INT,                             -- 估算 token 数，用于裁截断长
  fingerprint BIGINT NOT NULL,                 -- ★ LingChat 同款：hash(heading+text)
  created_at  TIMESTAMP
);

-- ③ 角色 ↔ 文档（多对多，就是"角色卡勾选多个 id"）
CREATE TABLE interviewer_knowledge (
  interviewer_code VARCHAR(32) NOT NULL,
  doc_id           BIGINT      NOT NULL,
  PRIMARY KEY (interviewer_code, doc_id)
);

向量放哪（这是个单独的选择）：见下节，两种都可。

选项甲（推荐起步）：单独一张表存 float 数组
CREATE TABLE knowledge_vector (
  chunk_id  BIGINT PRIMARY KEY,
  model     VARCHAR(64),                    -- 记录用的哪个 embedding 模型，换模型要重建
  dim       INT,
  embedding BLOB                            -- 512 × 4 字节 = 2KB/条；1000 条才 2MB
);
启动时全部读进内存 List<float[]>，暴力遍历算余弦 —— 几千条不到 10ms。

选项乙：和 chunk 放一起，加一个 embedding BLOB 列。更省事，但每次查 chunk 都要拖着 2KB。

5.2 导入脚本要做的事（你的"自动化切分"要求）

scripts/import_knowledge.py <角色> <目录或文件…>
  1. 扫 md（UTF-8）
  2. 按 markdown 标题层级切分          ← 比定长切好太多：一个二级标题 = 一个知识点
       ## 3.2 内存泄漏排查   → heading = "第3章 > 3.2 内存泄漏排查"
  3. 太长的块再按句号二次切 + 保留 15% 重叠
  4. 每个 chunk 追加 fingerprints = hash(heading + text)
  5. （可选 HyPE）调 LLM："这段能回答哪 3 个问题？" → 存进 questions 字段一并 embed
  6. 调 embedding 接口拿向量
  7. 幂等写库：fingerprint 没变 → 跳过；变了 → 更新；多余的 → 删
  8. 把 doc 挂到指定的 interviewer（写 interviewer_knowledge）
幂等这一点，对你说的「用户把 md 文件直接丢到那个目录」很重要 用户可能今天改一下 md、明天删一个。脚本必须能重复跑，不能每次全删重建（那样会反复耗尽 embedding 额度）。指纹比对就是为此存在的 —— 这是从 LingChat retrieval.rs:39-78 直接学到的一招。

6 · 一个绕不开的决策：embedding 从哪来

先讲死结：DeepSeek 官方不提供 /embeddings 接口。 你现在整个项目的 LLM 走的是 DeepSeek OpenAI 兼容端点，但那个端点只有 chat completions。向量得另想办法。
选项怎么落地成本取舍
A. 云端 embedding API
推荐		 换一家 OpenAI 兼容的服务，调它的 /embeddings。现有 LlmClient 复制一份改路径即可 中文小模型普遍很便宜，甚至有免费的 优点：零本地部署、Java 侧代码量最小、维度通常更高（1024）。
缺点：多一个 API key 要配；离线演示不了
B. 本地 ONNX
LingChat 的做法		 下 bge-small-zh-v1.5（约 100~200MB）+ onnxruntime-java，Java 里跑推理 一次性下载 + 依赖 优点：完全离线、免费、无 key，跟 LingChat 口径一致（写报告时"我们和上游同源"很好看）。
缺点：要引入 ONNX Runtime native 库，包体变大；512 维
C. 假 embedding（保底） 用 TF-IDF / 字符 n-gram 哈希当"向量"，纯 Java 实现 零成本 优点：永远能跑，答辩时断网也不怕。
缺点：效果远差于真 embedding —— 只能作为 A/B 都不可用时的兜底
建议：A 为主，C 兜底，B 写进"可选升级" 理由：课设答辩那天，最怕的是「网络/API 出问题 = 整个知识库功能演示不了」。所以搞一个 EmbeddingProvider 接口，三个实现随便切配置。这个抽象本身也是个很好的设计点可以写在报告里。

7 · 分批落地清单

批内容依赖验收标准
K1 三张表 DDL + 实体 + CRUD；EmbeddingProvider 接口 + 云端实现 + 假向量兜底 无 mvn test 通过；EmbeddingProvider.embed("你好") 返回定长 float[]，两种实现维度一致
K2 Python 导入脚本（markdown 标题切分 + fingerprint 幂等 + 写库）；不用 LLM K1 同一份 md 跑两次，chunk 数不变、第二次不调 embedding；改一个字重跑，只重算那一条
K3 检索服务：内存余弦 + 自写 BM25 + RRF + 阈值 K2 建 20 条真实问题的评测集，跑混合 vs 单路的命中对比，把曲线和阈值标定过程记下来
K4 接入 ChatService 自动注入（每轮都传真实输入，不走 rounds==0 那个坑） K3 端到端：问「内存泄漏怎么查」，SSE 回复里能看到引用了知识；问「今天天气」不注入
K5 前端：角色卡「岗位知识」多选 + 设置面板新 Tab（上传/列表/重新索引/试搜） K4 上传一个 md → 出现在列表 → 角色卡勾选 → 面试里生效
K6
二期		 HyPE：导入时给每个 chunk 生成假设问题 K3 同一评测集上，命中率相对纯 chunk 有提升（没提升就不要上，别为了炫技加复杂度）
K7
二期		 search_knowledge 工具 —— 需要先补聊天链路的工具闭环 K4 + 工具闭环 AI 在回答冷门技术问题时能自主触发工具，且知道什么时候不调
写进报告时最有价值的三句话
  1. 「单路向量检索对专有名词失效，因此采用 BM25 + 向量的混合召回，用 RRF 融合避免分数尺度不一致 —— 实测准确率从 72% 提升到 89%」
  2. 「检索结果采用带阈值的自动注入，且不写入对话持久层；阈值由 20 条真实问题的评测集标定」
  3. 「索引采用内容指纹增量更新策略，文档修改只重算受影响的片段，避免全量重建」
