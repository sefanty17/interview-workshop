# 自由对话模块 · 迁移整理

> 范围：**只整理「自由对话」一条链路**。剧本引擎（章节/事件）、TTS/ASR、Live2D、桌宠、工具调用、  
> 上帝 Agent、好感度、世界书、长期记忆压缩**不在本文范围**，单独整理。
>
> 结论先行：这条链路的骨架是 **6 个环节 + 1 个事件协议**，Java 侧需要落 5 个类 + 1 个 SSE 端点。  
> 真正的工作量在**提示词拼装**和**流式分句**两处，其余都是搬运。

## 四、数据模型对照

### 4.1 LingChat `line`（台词表，唯一真相源）

```rust
id, content,                      // 正文（不含【情绪】）
original_emotion,                 // 模型原始【情绪】标签
predicted_emotion,                // 分类器折叠后的 20 枚举之一
tts_content, action_content,      // <日语>、（动作）—— 解析后分列存储
audio_file, thinking,
attribute,                        // user | system | assistant | tool
sender_role_id,                   // 0 = 玩家，N = 角色，None = 旁白/工具
display_name,
save_id, tool_call, parent_line_id
```

### 4.2 我们的 `interview_message`（已建）

```
session_id, seq, role, content, original_tag, predicted_emotion, action
```

**对照缺口**：

| LingChat                        | 我们             | 处理                                    |
| ------------------------------- | -------------- | ------------------------------------- |
| `attribute`                     | `role`         | 值域改成 `user/system/assistant`（不用 tool） |
| `original_emotion`              | `original_tag` | 建议改名对齐（或文档锁定同义）                       |
| `tts_content`                   | 无              | **不迁**（不做 TTS）；`<日语>` 解析后直接丢弃         |
| `thinking你说了就是现在什么消息的什么表里面但实际上` | 无              | **不迁**（不做思考链展示）                       |
| `tool_call` / `parent_line_id`  | 无              | **不迁**                                |
| `sender_role_id`                | 无              | **不迁**（单面试官，role 字段足够）                |
| `save_id`                       | `session_id`   | 已等价                                   |

### 4.3 人设的存放方式 —— **关键差异**

LingChat **没有把 `persona_prompt` 存在角色表里**。`role` 表只有 `id / name / role_type /
resource_folder`（`db/entities/role.rs:19`）。人设是**一条 `attribute=system` 的 line**，  
排在台词表最前面，`sender_role_id = 该角色 id`，内容就是 `sys_prompt_builder` 拼装完的最终字符串。  
`MemoryBuilder` 见到它就直接 `LlmMessage::system(content)`（`memory_builder.rs:184`）。

我们目前把 `persona_prompt` 放在 `interviewer` 表里。两种做法：

| 方案    | 做法                                                                                 | 评价                                           |
| ----- | ---------------------------------------------------------------------------------- | -------------------------------------------- |
| A（推荐） | 开场时把「persona + 编排 + 格式要求」拼成完整 system 串，**作为首条 `interview_message`（role=system）落库** | 与 LingChat 一致；人设改动不会追溯污染历史场次；上下文组装只读台词表，逻辑最简 |
| B     | 每轮从 `interviewer.persona_prompt` 现场拼                                               | 少一次写入，但每轮都要重拼，且改了人设会改历史场次的复现结果               |

**选 A。** 这也顺带解决了你之前提的「面试编排要注入 system 且在角色页可编辑」——  
编排文本在开场时快照进那条 system 行，编辑只影响新场次。

## 五、System Prompt 拼装（原样照搬，字符串必须一致）

`utils/prompt.rs:183` `sys_prompt_builder`，中文模式拼接顺序**固定**：

```
① ai_prompt                        ← 人设本体（角色卡的 system_prompt）
② build_framing_prefix_cn(user, char)   ← 「你现在扮演…，我是…」的框架句
③ DIALOG_FORMAT_PROMPT_CN          ← 对话格式要求（多段「台词」、两句以内、禁颜文字…）
④ DEFAULT_EXAMPLE_CN               ← 内置示例
⑤ EXAMPLE_CUSTOM + 角色自带示例      ← 角色卡里有 example_dialogue 才加
⑥ DIALOG_FORMAT_PROMPT_2_EMOTION_LIMIT_HEAD  ← 情绪标签限制头
⑦ DIALOG_FORMAT_PROMPT_2_BODY      ← 正文要求
```

三个硬性判断（会改变输出，别省）：

1. `ai_prompt` 里含「日语翻译」→ 警告并**原样返回**，不拼格式；
2. 含「以下是我的对话格式提示」→ 判定为旧版角色，**原样返回**，不重复拼；
3. 中日双语模式换用 `_JP` 版本常量（本项目不做 TTS，**只实现中文分支**）。

> 我们项目的差异点：要在 ① 之后、② 之前插入**面试编排段**（本次面试岗位、流程顺序、  
> 关键轮次判断、节奏），因为这是 LingChat 没有的业务。插在这里而不是另起 system 消息，  
> 是为了保持「一条 system 行」的模型结构。

常量原文在 `utils/prompt.rs:33-162`（`DIALOG_FORMAT_PROMPT_CN` / `_JP` /  
`_2_EMOTION_LIMIT_HEAD` / `_2_BODY` / `DEFAULT_EXAMPLE_CN` / `_JP` / `EXAMPLE_CUSTOM`），  
共约 130 行中文。**逐字复制，不要改写**——格式要求是模型输出可被 `【】` 解析的前提。

## 六、流式分句（`StreamProducer`）

不是"按句号切"，而是**按情绪标签边界切**（`producer.rs:89`）：

```
状态：缓冲 buffer、句子序号 index、是否已发收尾句
遇到 chunk：
  ├ 已在 tag 内（见过【未见过】）→ 累积
  ├ 遇到【 → 进入 tag 状态
  ├ 遇到】→ 记 tag 结束，继续累积正文
  └ 再遇到【 → 把「buffer 至今」切成一个完整句子，投递 (text, index, false)
流结束：剩余 buffer（tag + 尾部正文）单独投递，标记 is_final = true
```

要点：

- **与网络 chunk 大小无关**，只依赖标签边界；
- `【1】` 这类数字标签同样处理；
- 工具闭环相关逻辑（`BeforeTools` 栅栏、去重、pending_sentence）**全部删除**；
- 越界保护：见到回合结束标记后，后续内容一律丢弃（`turn_ended`，`producer.rs:110`），  
  否则模型替玩家说的话会被写进台词表，下一轮又被当历史读回去。

Java 实现：`Flux<String>` 逐 chunk 喂给一个 `SentenceSplitter`，产出 `Flux<Sentence>`，  
再由上层组装成 SSE 事件。

## 七、符号解析（`MessageProcessor`）

六条正则，全部 `OnceLock` 单例（`processor.rs:48-73`）：

| 用途      | 正则                               |                     |
| ------- | -------------------------------- | ------------------- |
| 情绪 + 正文 | `【([^】]*)】([^【】]*)`              |                     |
| 日语      | `<([^>]*)>`                      |                     |
| 动作      | `（([^）]*)）` ← **全角括号**           |                     |
| 花括号块    | `\{([^}]+)\}`                    |                     |
| 临时段     | `(?s)\[!Temp!\](.*?)\[/!Temp!\]` |                     |
| 剥剩余标签   | \`<[^>]*>                        | （[^）]*）`/`【[^】]*】\` |

每个匹配产出一个 `EmotionSegment`：

```
index, original_tag, following_text, motion_text, japanese_text,
predicted, confidence, voice_file
```

- `predicted`：情绪分类器折叠结果；未启用分类器时 = `original_tag`。我们已把 82 个别名映射  
  离线做好了（`data/seed/emotions.json`），**Java 侧查表即可，不引入分类器**。
- `japanese_text`：本项目不做 TTS，**解析后直接丢弃**。
- `voice_file`：不迁。

`append_user_message`（`:264`）另外做两件事：

1. 抽出 `[!Temp!]…[/!Temp!]` 段，从用户正文里删掉，返回 `{main, temp}`；
2. 把时间感知提示（"（距离上次对话已过 N 分钟）"）按 `time_sense_enabled` 挂上。

## 八、事件协议（SSE 对齐点）

`responses.rs` 的 `ReplyResponse`，序列化后字段名是 **camelCase**（`#[serde(rename_all)]`）：

| 字段                                | 类型      | 说明              | 我们                     |
| --------------------------------- | ------- | --------------- | ---------------------- |
| `type`                            | string  | `"reply"`       | 保留                     |
| `isFinal`                         | bool    | 最后一句为 true      | **保留，前端靠它复位**          |
| `duration`                        | f64     | 展示时长            | 保留                     |
| `message`                         | string  | 本句正文（已剥标签）      | 保留                     |
| `originalMessage`                 | string  | 原始含标签文本         | 保留                     |
| `emotion`                         | string  | 折叠后情绪（立绘用）      | 保留                     |
| `originalTag`                     | string  | 原始情绪标签          | 保留                     |
| `motionText`                      | string? | 动作文本            | 保留（灰色显示）               |
| `character` / `roleId`            |         | 说话者             | 保留 character，roleId 可空 |
| `displayName` / `displaySubtitle` |         | 标题栏             | 保留                     |
| `userMessageSeq`                  | u32?    | 触发本轮的 user 消息序号 | 保留（回溯定位用）              |
| `ttsText` / `audioFile`           |         | TTS             | **不迁**                 |
| `thinking`                        |         | 思考链             | **不迁**                 |
| `previewGen`                      |         | 编辑器试玩代号         | 不迁                     |

事件名固定四个：

```
ai:reply       每句一个
ai:thinking    开始/结束思考（{isThinking, duration}）
status:reset   强制复位 input（不报错）
ai:error       {errorCode, detail}，同时复位
```

**Java 侧改成 SSE**：`text/event-stream`，`event:` 用同名四值，`data:` 放同结构 JSON  
（字段名一字不改，前端只改传输层）。断线语义：`ai:error` 之后必须能重新发。

## 九、记忆构建（`MemoryBuilder::build`）

台词表 → `Vec<LlmMessage>`，规则不复杂但**边界容易写错**：

1. 遍历台词，按属性分三类累积：
   - `system` 且 `sender_role_id == 目标角色` → 直接 `system(content)`，**只取第一条**，  
     重复的忽略并告警（`memory_builder.rs:184`）；
   - `assistant`（本角色说的，或 `perceived_role_ids` 含本角色）→ 连续多句**合并成一条  
     assistant 消息**，每句格式：`【情绪】正文\n(动作)\n\n`，整段末尾再加一个 `\n`；
   - 其它（user / 旁白 / 其他角色）→ 合并成一条 `user` 消息，格式：  
     有上下文时 `{其他角色台词 \n …}\n\n玩家台词`；单人纯对话**不加「名字:」前缀**，  
     有旁白/多角色时才加。
2. 空行数量是刻意的：句间一个空行、轮末两个空行——给模型一个「本轮到此为止」的可见边界，  
   流式侧也按这个边界截断越界内容。
3. `truncate_at_turn_end`：每句内容先截到回合结束边界，防止历史里夹带模型替玩家写的台词。
4. 窗口切片（`role_manager.rs:375`）：默认取全量 + 前缀裁切；**我们不做长期记忆压缩**，  
   直接全量，超过 `maxTokens` 时按「最旧的 user/assistant 对」成对丢弃。

我们没有 `line_perception`（多角色感知表），单面试官下 `is_target` 判据退化为  
`sender_role_id == 面试官`，可以直接合并逻辑。

## 十一、建议的迁移顺序（每步可独立验收）

| 步      | 内容                                                 | 验收标准                                                        |
| ------ | -------------------------------------------------- | ----------------------------------------------------------- |
| **F1** | `PromptAssembler` + `MemoryBuilder` + 单测           | 给定固定台词表，输出的 `LlmMessage[]` 与 Rust 版逐字节一致（用同一份台词做快照对比）       |
| **F2** | `SentenceSplitter` + `SymbolParser` + 单测           | 输入一段含多层 `【】（）` 的文本，切出的句子序列与 `processor.rs` 一致（照抄 Rust 单测用例） |
| **F3** | `ChatService` + `POST /api/chat/{id}/messages` 非流式 | 能真调 DeepSeek 拿完整回复，落库成 line，再拼下一次上下文                        |
| **F4** | SSE 化 + 前端 `useChat()` 接上                          | 前端逐句显示、情绪切立绘、`isFinal` 复位输入框                                |

F1/F2 是纯函数，可以先写先测，不依赖数据库和网络——建议先做这两步。

## 十二、需要你拍板的两件事

1. **人设快照落库**（§4.3 方案 A）：开场时把拼好的 system 串写成首条 `interview_message`。

   保持"一条 system 行"。另一种是作为独立 system 消息放最前面（模型权重更高）。  
   选哪个？
